# Notes: User Authentication

Append-only log of decisions, deviations from the plan, and tradeoffs made during implementation. Do not edit or delete earlier entries — add new dated entries below.

## 2026-09-22

Sparring partner review of `plan.md` (Phase 2, pre-approval):

- **Attack:** (1) Single shared `email` identifier means there's no separate username — if a future feature wants a public-facing display name distinct from email, this becomes a breaking schema change. (2) bcrypt's 72-byte input cap is an easy-to-miss footgun — if the request schema doesn't enforce it, longer passwords get silently truncated by the library, creating a subtle security/UX bug. (3) The plan claims login timing will be made "comparable" via a dummy-hash comparison, but doesn't specify *how* that dummy hash is generated/stored consistently — if implemented sloppily (e.g. hashing a literal on every call vs. a precomputed constant), the mitigation could itself vary in cost and leak the same signal it's meant to hide. (4) `JWT_ACCESS_TOKEN_EXPIRE_MINUTES` default of 30 minutes with no refresh/logout mechanism forces re-login every 30 minutes — plan doesn't flag this as a real UX tradeoff, just a security one.
- **Steelman:** (1) No requirement anywhere calls for a distinct username; adding one now would be speculative. (2) The cap is explicitly called out in ADR-1 and enforced at the schema level, not left implicit — the risk is implementation discipline, not a plan gap. (3) The mitigation direction (always do comparable work) is the standard fix for this exact class of bug; the plan correctly identifies the right technique even if the precise dummy-hash mechanics are an implementation detail, not a planning-level decision. (4) 30 minutes is a reasonable, conservative default for a v1 system with no revocation — short-lived tokens are the standard compensating control when there's no refresh/logout.
- **Verdict:** (1) and (4) are accepted as-is — no plan change needed, both already have explicit reasoning in ADR-2/Risks. (2) is fine as planned; flagged here as something to verify during implementation/testing (a test asserting a 73-byte password is rejected with 422, not silently truncated). (3) is the one gap worth tightening: added a concrete mechanism to the plan (Risks section) — the dummy hash must be a fixed, precomputed bcrypt hash of a constant string, computed once at startup/import time, not recomputed per request, so its cost is stable and comparable to a real lookup.

## 2026-09-22 (implementation)

Deviations/clarifications made during Phase 4 implementation, none of which change the approved contract in `plan.md` (data model, API contracts, ADR-1/2/3 all implemented as specified):

- **Email format validation implemented without the `email-validator` package.** `plan.md`/`tasks.md` don't name a specific email-validation library, and the requirements.txt list in T001 doesn't include one. Used a small `re.fullmatch` pattern in `app/schemas/user.py` instead of Pydantic's `EmailStr` (which requires `email-validator`), to avoid introducing a dependency not named in the plan. Also normalizes email to lowercase at the schema level (both `UserCreate` and `LoginRequest`) so registration uniqueness (FR-002) and login (FR-004/FR-005) aren't defeated by casing differences — the plan's data model doesn't call out case-sensitivity, and case-insensitive treatment is the safer default for an email-as-identifier scheme.
- **bcrypt hashing/verification is off-loaded to a worker thread** (`hash_password_async`/`verify_password_async` in `app/core/security.py`, via `anyio.to_thread.run_sync`) rather than called synchronously from the async request path. `plan.md` doesn't mention this explicitly, but CLAUDE.md requires async I/O for the running app to stay responsive under load, and bcrypt's ~100-300ms CPU cost would otherwise block the single event loop for every register/login call. `AuthService` calls the async wrappers; the dummy-hash timing-safety mechanism from the Risks section is preserved unchanged.
- **Transaction commits moved from the repository layer to the service layer.** The repository methods (`UserRepository.create`) now `flush()` only; `AuthService` calls `session.commit()`/`session.refresh()` after a successful repository call, and `session.rollback()` on `IntegrityError`. This wasn't explicit in `plan.md`, but matches its stated layering principle ("service layer... only layer allowed to make decisions about what should happen") and keeps the transaction boundary owned by the layer that will need to coordinate multi-repository units of work as more features land.
- **Test suite uses a fresh, per-test SQLAlchemy engine (NullPool) instead of the app's module-level engine.** Discovered during implementation: pytest-asyncio's default per-test-function event loop is incompatible with reusing one long-lived async engine/connection pool across tests (asyncpg connections are bound to the loop that created them, causing "attached to a different loop" / "another operation is in progress" errors). `tests/conftest.py`'s `db_session` fixture builds a disposable engine per test and overrides the `get_db` dependency; this is test-infrastructure only and doesn't affect the running application's engine/pooling behavior.
